## How the pin is enforced

- `requirements.in` uses the immutable git URL form:
  ```
  apexomni @ git+https://github.com/ApeX-Protocol/apexpro-openapi.git@4d849dd84087b9551afaa55d5f37068f7ce0a103
  ```
- `requirements.lock` is generated with `pip-compile --generate-hashes
  --allow-unsafe`. Every non-git dependency has a `--hash=sha256:...` line;
  `pip install --require-hashes -r requirements.lock` fails the build if
  any dependency (or its hash) changes.
- The git dependency itself is pinned by full commit SHA, which is a
  content hash. Rewriting history at that SHA would require SHA-1 preimage.
- CI/Docker build re-runs `pip install --require-hashes` from an empty
  cache; a floating dependency causes a hard build failure.

| Package     | Version | ID                | Fix     |
|-------------|---------|-------------------|---------|
| ecdsa       | 0.16.0  | PYSEC-2026-1325   | (none)  |
| ecdsa       | 0.16.0  | PYSEC-2026-2467   | 0.19.2  |
| mpmath      | 1.0.0   | PYSEC-2021-427    | 1.3.0   |
| setuptools  | 80.10.2 | PYSEC-2026-3447   | 83.0.0  |

These pins come from the SDK's `pyproject.toml` (`ecdsa==0.16.0`,
`mpmath==1.0.0`, `setuptools<81`). They are not fixable without patching
the SDK. The signer service:

- does NOT use `ecdsa` for signing (we use `eth_account` via
  `web3==6.0.0`, which uses `coincurve` internally);
- does NOT expose `mpmath` to untrusted input;
- pins `setuptools` only for the SDK's runtime import of `pkg_resources`.

Owner action: track these upstream in the ApeX Omni SDK issue tracker
and re-pin when a patched release ships. This is a documented residual
risk, not a build blocker.
